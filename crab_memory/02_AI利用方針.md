# 検討2: アプリ内にAIを用いるべきか

## 1. 結論

**用いるべき。** ただし「AIに全部やらせる」のではなく、

- 決定的にできる処理はルールで行い、
- 文脈理解が必要な処理だけ AI（LLM）に任せ、
- AI の出力は固定スキーマの JSON に限定し、
- 図の描画はプログラムが行う

という分業にする。

## 2. 理由

### 2.1 タスクの性質

「文と文の繋がりを把握する」は NLP でいう談話関係認識（discourse relation recognition）にあたり、長年の難問。

- **明示的な関係**（接続詞あり）: 辞書照合でかなり取れる。「しかし」→逆接。
  ただし多義性（「そして」）や、接続詞と実際の論理が食い違う文もある。
- **暗黙的な関係**（接続詞なし）: 文脈の意味理解が必要。日本語は接続詞を省く文章が多く、
  「うまい文章」ほど省かれる傾向がある。ここは従来手法では実用精度に届かない。
- **ノードの要約**（図のラベル生成）: 生成タスクなので LLM 向き。
- **役割付け**（主張か根拠か）: 文脈理解が必要で LLM 向き。

「独自プログラムに係数を持たせて誘導する」というアイデアは、実質的に自前で分類器を学習させることに相当する。
学習データ（人手で関係を付けた日本語コーパス）と計算資源が必要で、しかも出来上がるものは LLM の劣化版になりやすい。
この直感（その手法は AI に似ている）は正しく、そこは LLM を使うのが現実的。

### 2.2 従来 NLP だけで作る選択肢

- 形態素解析（MeCab / Sudachi / GiNZA）＋接続詞辞書: 明示関係のみ扱える。無料・高速・決定的・オフライン。
- 日本語談話関係コーパスで学習済みの分類器: 公開されていて実用になるものは少ない。自作は工数が大きい。

→ 従来 NLP は「前処理」と「明示関係の下書き」に使い、その結果を AI に判断材料として渡す。

## 3. 役割分担（ハイブリッド設計）

| 処理 | 方式 | 理由 |
|---|---|---|
| 段落・文の分割 | ルール | 決定的、無料、高速 |
| 接続表現の検出 | ルール（辞書） | AI へのヒント、根拠の説明に使える |
| 関係型の確定（明示＋暗黙） | LLM | 文脈理解が必要 |
| ノードの要約ラベル | LLM | 生成タスク |
| 役割付け（主張/根拠/例…） | LLM | 文脈理解が必要 |
| JSON のスキーマ検証 | ルール | LLM の逸脱を弾く |
| レイアウト・描画 | プログラム | 再現性。AI に図を描かせない |
| 手動修正の反映 | プログラム | ユーザーの判断が最優先 |

## 4. AI を使う際の設計上の論点

1. **出力の固定化**: 構造化出力（JSON スキーマ）で関係型を enum に縛る。自由文は返させない。
2. **根拠の提示**: 各エッジに「根拠となる語句」（evidence）を返させる。
   ユーザーが誤りに気づけるうえ、「なぜそう繋がるか」を示すこと自体が読解補助の機能になる。
3. **誤りへの対処**: 信頼度を付け、低いものは点線で描く。ユーザーが関係を修正できる UI をデバッグ機能として MVP に含める（Q7）。
4. **長文の扱い**: 段落・章ごとに分割して処理し、段落間の関係は各段落の要約を元に別途推定する。
   処理結果はキャッシュし、同じ文章を再送しない。
5. **コストとレイテンシ**: 2000字程度の論説文なら 1 回あたり数円〜十数円の見込み（要計測）。デモでは問題にならない。
   小説一冊（10万字超）は段落単位の分割と非同期処理（バッチ）が前提になる。
6. **プライバシー**: 入力文章が外部 API に送られる。個人の文書や未公開原稿を扱うなら告知が必要。
   ローカル LLM は選択肢になるが精度は落ちる。
7. **評価の物差し**: 10〜20 本の文章に人手で正解の関係を付けた小さなデータセットを作り、精度を測る。
   これが無いとプロンプト改善が勘頼みになる。
8. **決定性**: 同じ文章で毎回結果が変わると読解補助として混乱する。結果を保存して再利用し、
   再生成は明示的な操作にする。

## 5. モデル・実装の選択肢（Q6「費用をかけたくない」を受けて）

| 選択肢 | 精度 | 費用 | プライバシー | 備考 |
|---|---|---|---|---|
| ルールのみ（接続表現辞書） | 低（明示関係のみ） | 0 | 手元で完結 | ステップ0。最初に作る |
| ブラウザ内 LLM（WebLLM / Transformers.js） | 中〜低 | 0 | 手元で完結 | 初回に数 GB のモデル取得。日本語の小型モデルで関係推定が安定するかは要検証 |
| 外部 API（各自のキーで従量課金） | 高 | 少額 | 外部送信あり | サーバーを持たず、ブラウザから直接呼ぶ（04 §1） |
| ローカル LLM（Ollama 等） | 中 | 0（要 GPU） | 手元で完結 | Web アプリからローカルサーバーへ接続する形。設定が増える |

AI 呼び出しは 1 つのアダプタの裏に隠し、上の 4 つを設定で切り替えられるようにする。
「費用ゼロ」を厳密に取るなら上 2 つ、少額を許容するなら外部 API が本命 → Q11。

### 費用の試算（外部 API、Claude を使う場合。2026-06 時点の価格）

2000 字の論説文 1 本を処理するとき、入力はシステムプロンプト込みで約 3,000 トークン、出力（JSON）は約 2,000 トークンと見積もる。

| モデル | 入力 $/1M | 出力 $/1M | 1 本あたり | 100 本 |
|---|---|---|---|---|
| `claude-opus-5` | 5 | 25 | 約 $0.065（約 10 円） | 約 $6.5 |
| `claude-sonnet-5` | 2 | 10 | 約 $0.026（約 4 円） | 約 $2.6 |
| `claude-haiku-4-5` | 1 | 5 | 約 $0.013（約 2 円） | 約 $1.3 |

- 開発中に 100 本処理しても数百円〜1,000 円程度。「完全ゼロ」でなければ現実的。
- 結果をキャッシュし、同じ文章を再送しないだけで大きく減る（§4-8）。
- 実装するなら構造化出力（`output_config.format`、SDK では `messages.parse()`）で JSON を固定し、
  関係型の定義などの固定部分はシステムプロンプトの先頭に置いてプロンプトキャッシュを効かせる。
- 言語は TypeScript を提案（04 §4）。SDK は `@anthropic-ai/sdk`。

## 6. 「AI なし」で作れる部分を先に作る

接続詞だけを手がかりにした可視化は AI なしで作れる。これを**ステップ0**として先に作ると、

- パイプライン（分割 → JSON → 描画 → UI）の全体を早く通せる
- AI 層の価値（暗黙関係の補完）が「ステップ0との差分」として測れる
- API キーやコストの話を後回しにできる

という利点がある。デモ設計としても、ルール版 → AI 版の比較を見せられる。

**決定**: Q6（費用をかけない）を受けて、ステップ0（ルールのみ）を最初に作ることを確定する。AI 層は 04 §3 の段階で追加する。
