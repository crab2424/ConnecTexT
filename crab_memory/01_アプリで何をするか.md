# 検討1: アプリ内で何をするか

## 1. 前提の整理

- 動機（memo.txt）: 小説などの長文を読むのが苦手 → 文章の論理構成を図で可視化したい。
  「こうだからこうなる」という論理展開が見えれば、レポート・作文・読解に役立つ。
- 目的: **読解補助**。文章 → 構造の抽出 → 図示、という流れ。
- 品詞分解・文法解析は主目的ではない。ただし文分割や接続表現の検出には最低限使う（後述）。

## 2. 「論理展開」とは何を指すか（最重要の論点）

「展開」の中身は文章の種類によって変わる。ここを決めないと、図の形も抽出すべき情報も決まらない。

| 文章の種類 | 「展開」の実体 | 図のノードになるもの | 関係（エッジ）の例 |
|---|---|---|---|
| 論説文・評論・レポート | 主張と根拠の構造 | 命題（文・節） | 主張→根拠、根拠→例示、逆接、結論 |
| 説明文・教科書 | 概念の定義と因果・分類 | 概念、命題 | 定義、原因→結果、条件、分類 |
| 小説・物語 | 出来事の因果・時系列・人物関係 | 出来事、場面、人物 | 前後、原因→結果、場面転換、伏線→回収 |

読み手が迷子になる原因も違う。

- 論説文: どれが主張でどれが根拠か分からない。どこで話が反転したか見失う。
- 小説: 誰が何をしたか、今どの場面か、この出来事の原因は何か、を追えなくなる。

**提案**: 中間表現（ノード＋関係型）は共通にしておき、**最初のデモ対象は論説文・説明文に絞る**。

理由:
1. 接続表現（だから・しかし・例えば）で関係が明示されやすく、精度が出やすい。
2. 「正しい図」を自分で判定しやすいので、AIの出力の良し悪しを検証できる。
3. memo にあるレポート・作文への応用は、論説文の構造理解と直結する。

小説は「論理」というより「出来事の因果と時系列」の可視化になり、人物・場面という別のノード種が必要になる。
第2段階として、中間表現を拡張して対応する。→ [03_未決事項と質問.md](03_未決事項と質問.md) の Q1

## 3. 中間表現（アプリの中核）

図を直接生成するのではなく、まず「構造」を固定フォーマット（JSON）で表し、図はそこから機械的に描く。
これにより、AIの入れ替え・図の表現方法の変更・手動修正がそれぞれ独立してできる。

### 3.1 ノード

- `id`, `text`（原文の範囲）, `summary`（10〜20字の要約。図のラベル）, `paragraph`（所属段落）
- `role`（論説文向け、任意）: 主張 / 根拠 / 事実 / 例 / 反論 / 譲歩 / 結論 / 問い

### 3.2 関係タイプ（エッジ）の候補

日本語の接続表現を出発点に、談話関係理論（RST, PDTB）を参考にしつつ、読解補助に必要な最小セットに絞る。

| 型 | 典型的な接続表現 | 意味 |
|---|---|---|
| 因果・順接 | だから、したがって、そのため、〜ので | AだからB |
| 理由 | なぜなら、というのも | BなのはAだから（因果の逆向き） |
| 逆接・対比 | しかし、だが、一方、ところが | Aに反してB |
| 譲歩 | 確かに〜が、もちろん〜しかし | Aは認めるがB |
| 例示・具体化 | 例えば、具体的には | AのインスタンスがB |
| 言い換え・要約 | つまり、要するに、すなわち | A＝B |
| 添加・並列 | また、さらに、そして | AとB |
| 条件・仮定 | もし〜なら、〜すれば | Aの場合B |
| 帰結・結論 | 以上より、このように、よって | Aから結論B |
| 転換 | ところで、さて | 話題が変わる（エッジではなく区切りマーカー） |

注意点:
- 接続詞は多義（「そして」は並列にも順接にもなる）。
- 日本語では接続詞を省いた**暗黙の関係**が非常に多い（「雨が降った。試合は中止になった。」）。
  ここがルールだけでは扱えない部分 → [02_AI利用方針.md](02_AI利用方針.md)
- 型を増やしすぎると図が読めなくなる。初期は 6〜8 種に絞り、色・線種で区別できる数に抑える。

### 3.3 エッジ

- `from`, `to`, `type`（上記の enum）, `evidence`（根拠となる語句。「しかし」など）, `confidence`（0〜1）, `explicit`（接続詞が明示されているか）

## 4. 処理パイプライン案

1. **入力**: テキスト貼り付け（MVP）。将来: ファイル読み込み、画像 OCR。
2. **前処理（決定的）**: 段落分割、文分割、接続表現の検出。
3. **構造抽出（AI＋ルール）**: ノードの要約、関係型の確定、役割付け。
4. **中間表現 JSON**（スキーマ検証）。
5. **レイアウト＆描画**（プログラム。AIには描かせない）。
6. **対話**: 本文⇔図の相互ハイライト、ノードの展開/折りたたみ、関係の手動修正。

## 5. 可視化方式の比較

| 方式 | 長所 | 短所 | 向く場面 |
|---|---|---|---|
| A. 静的グラフ（ノード＋矢印、自由配置） | 全体を俯瞰できる、印刷・画像出力しやすい | 長文で線が絡む、読み順が分かりにくい | 短い論説文 |
| B. 階層ツリー / アウトライン（主張→根拠→例） | 論説文と相性が良い、線が絡まない | 逆接・往復する議論を表しにくい | レポート、評論 |
| C. 読み順の縦フロー（段落を縦に並べ、関係を横・斜めの矢印で） | 本文との対応が取りやすい、時系列が自然 | 遠い文同士の関係は長い矢印になる | 説明文、小説 |
| D. ステップ再生（読み進めるごとに図が育つ） | 「展開」を時間で体感できる、実装はA/Cに順序を足すだけ | 全体俯瞰には一度再生が必要 | 読解補助全般 |
| E. 動詞のアニメーション（出来事を動きで表現） | 直感的 | 動詞ごとに表現を作る量が膨大。論理関係の可視化とは別問題 | 物語の場面理解（将来） |

### 「時間というパラメータ」への回答

時間軸は入れる価値がある。ただし「動詞をアニメで表す」のではなく、
**「読み進める順序」を時間軸として、図が構築されていく過程を再生する**（D）のが本命だと考える。

- 論理展開は「前の文を受けて次の文がどう繋がるか」の積み重ねなので、構築過程そのものが展開の可視化になる。
- 実装コストは静止画＋順序情報だけで済み、静止画（全体俯瞰）と両立する。
- 動詞のアニメ化（E）は「文の内容」を可視化するもので、「文と文の論理関係」の可視化とは目的が異なる。
  小説対応のときに再検討する。→ Q8

**提案**: C（縦フロー）を基本レイアウトにし、D（ステップ再生）を重ねる。論説文では B（階層）への切り替えも用意する。

## 6. 図の表現要素（案）

- ノード: 要約ラベル。クリックで原文を表示。役割（主張・結論）で枠の太さや色を変える。
- エッジ: 関係型ごとに色と線種を固定する。例: 因果＝実線矢印、逆接＝赤の折れ矢印、例示＝点線、言い換え＝二重線、並列＝矢印なし。
- 暗黙の関係（接続詞なし）や信頼度の低いものは薄く・点線で描き、AIの推定であることを示す。
- グループ: 段落・節を枠で囲む。
- 転換点マーカー: 話が反転・転換する箇所に印を付ける。
- 本文パネルと図パネルの相互ハイライト。

## 7. MVP（デモ）のスコープ案

- 入力: 日本語の論説文、500〜2000字。
- 出力: 中間 JSON → 縦フロー図 ＋ ステップ再生。
- 本文と図の相互ハイライト。
- 関係の手動修正、画像エクスポート、小説対応は第2段階。

## 8. 参考になる既存の考え方

- Toulmin モデル（主張・根拠・論拠）: 論説文の役割付けの参考。
- RST（Rhetorical Structure Theory）, PDTB: 談話関係の分類の参考。
- Argument mapping ツール（Rationale, Argdown, Kialo）: 論理構造の図示の先行例。ただし人が手で構造を書く前提。
- マインドマップ・アウトライナ: 階層表示の UI の参考。

本アプリとの違いは、**既存の文章から自動で構造を抽出する**点と、**本文と図の対応を常に保つ**点。
